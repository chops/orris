** Implementation status
:PROPERTIES:

(~lib/ai_orchestrator/dispatch/local_pane.ex~) sends and reconciles with

*** Why this pin stays over the whole producer document
:PROPERTIES:
:CUSTOM_ID: why-this-pin-stays-over-the-whole-producer-document
:END:
The producer copy records a cheaper shape for this side to adopt and leaves the
choice here: pin the producer's VENDORED-REGION digest (its ~source_sha256~)
instead of the whole-document digest, because that "would be stable across
producer addenda edits and would end the alternation". Measured at ~d6b2e369~
before deciding, and declined for two reasons that are facts rather than taste.

It carries no information this block does not already carry. The producer's
vendored region is 12671 bytes digesting to
~939e09474dce6cf82af1dff19c8880b2c5148c6b2c4d4fb10da60fdf8a4a5be5~, and that is
byte-for-byte the digest of THIS file at ~3684f53e~ -- which was the
~vendored_source_sha256~ declared at that pairing. Pinning it would replace a statement about the
producer's document with a restatement of this repository's own bytes,
reproducible here without ever consulting the producer. The whole document is
24414 bytes, so 11743 bytes of producer material -- its own pairing block, its
addenda, its fixture inventory -- would leave the pin's scope, and a reader
comparing the two copies would no longer be told when any of it moved.

It would not end the alternation either. The alternation exists because each
side's pin lives INSIDE the bytes the other side vendors, not because of the
digest's scope: this very edit changes this file, so the producer's region no
longer equals this file at HEAD and the next re-taking is owed exactly as before.
A digest over a narrower region alternates on the same schedule.

What the cheaper shape would genuinely remove is invalidation caused by producer
addenda edits alone. That is a real cost, and it is the price of the pin saying
something about the producer at all. It stays whole.

The measurement above is the one taken at ~d6b2e369~ and is left as the dated
record of that decision. Re-measured at the current pairing ~7e5f5321~ the
arithmetic is the same shape and the conclusion is unchanged: the producer's
vendored region is 36410 bytes digesting to
~dd121abbd0f4596889d6960b4c1a6273f5c44e3fb6a463b9a56c8b7cc9973315~, which is the
digest of THIS file at ~ffe6fb87~ and is already declared above as
~vendored_source_sha256~; the whole producer document is 52344 bytes, so 15934
bytes of producer material would leave the pin's scope. The pin stays whole.

** Framing and version
:PROPERTIES:
:CUSTOM_ID: framing-and-version
:END:
- A request that carries ~"protocol_version": 2~ is a v2 request. Every v2 reply
  carries ~"protocol_version": 2~ and ~ok~, and every v2 reply to a message-bound
  command echoes both ~msg_id~ and ~pane_id~. A reply without the version, or a v1
  reply to a v2 request, is not a v2 answer and a client MUST refuse it.
- ~ping~ with ~protocol_version~ 2 answers ~capabilities~, a list of tokens.
  ~delivery_reconcile~ is the token that authorizes a client to send at all
  (the client fails closed without it: it cannot ask what became of a send).
- A v2 ~send~ MUST carry ~msg_id~ (the client's send id); the daemon hashes the
  text it is given itself, so a send carries no payload hash and ~missing_msg_id~
  is the refusal. ~reconcile~ carries the ~payload_hash~ (~sha256:~ + 64 lowercase
  hex over the exact bytes) and is refused with ~missing_payload_hash~ without it.
- ~reconcile~ carries ~msg_id~, ~payload_hash~, ~pane_id~; the answer is one of
  exactly five ~outcome~ values: ~delivered~, ~queued~, ~absent~, ~ambiguous~,
  ~conflict~. ~not_delivered~ is a stored status that answers ~absent~; ~pending~
  answers ~ambiguous~ after the daemon's bounded wait. ~absent~ and ~conflict~
  carry no receipt view; ~conflict~ echoes the identities the caller presented,
  never the stored ones.

** Identity grammars and their refusals
:PROPERTIES:
:CUSTOM_ID: identity-grammars-and-their-refusals
:END:
- ~msg_id~ is ~snd_~ followed by exactly 64 lowercase hex characters (the
  SEND-ID-1 digest; the minting rule is the client's, the grammar is shared).
- ~pane_id~ is ~%~ followed by 1..128 characters from ~[a-zA-Z0-9_]~. This is the
  GOVERNING grammar: it is the one the daemon's receipt record is keyed by, so a
  pane id outside it cannot be stored and therefore cannot be delivered. A daemon
  whose echo predicate is wider than its storage predicate will echo a pane id it
  then refuses; the two predicates are one grammar and a daemon reconciles them on
  its own side.
- An identity that fails its grammar is refused ~invalid_msg_id~ or
  ~invalid_pane_id~ BEFORE admission. The daemon drops the echo for the identity
  it could not read -- there is nothing safe to echo -- so these replies carry at
  most the other identity, and a client MUST NOT require an echo before naming
  them. They are request errors, facts about the request the client built, and are
  distinct from ~missing_msg_id~ / ~missing_pane_id~, which say the field was
  absent rather than malformed.

** Reconcile replies
:PROPERTIES:
:CUSTOM_ID: reconcile-replies
:END:
~reconcile.<outcome>.json~ for the five outcomes; ~delivered~, ~queued~ and
~ambiguous~ carry the receipt view (~status~, ~delivery_attempt~, identities).
~absent~ comes in two shapes: no record at all (~reconcile.absent.json~, echoed
identities only, which a client reads as attempt 0) and a stored absence
(~reconcile.absent.not_delivered.json~: ~status~ ~not_delivered~ with the
positive ~delivery_attempt~ it closed) -- the client's retry bound depends on
that distinction, so a stored receipt without a positive attempt is refused.
~conflict~ carries only the identities the caller presented.

*** What ~sessions~ answers
:PROPERTIES:
:CUSTOM_ID: what-sessions-answers
:END:
- The command is ~sessions~ at ~protocol_version~ 2. It takes no project filter
  and no lifecycle option. It is a read: it answers what one observation of the
  session census said, and nothing else.
- A daemon that implements it advertises ~sessions_read~ in its ORDINARY v2
  ~ping~ reply, beside ~delivery_reconcile~. There is no second ping, no opt-in
  dialect and no query parameter that reveals the capability to some callers and
  hides it from others: one ping answers one capability list. ~sessions_read~
  authorizes the read exactly as ~delivery_reconcile~ authorizes a send, and a
  client that does not see it MUST NOT issue ~sessions~ at all.
- A successful reply carries exactly three keys: ~protocol_version~, ~ok~ and
  ~sessions~. There is no ~pong~, no count, no timestamp and no echo.
- ~sessions~ carries exactly ONE object per ~session_id~ observed, and that
  object collects every address observed for that session. A session is never
  split across two objects, and two objects never share a ~session_id~. Grouping
  is by the stable id, never by the reusable ~session_name~.
- Each element of ~sessions~ carries exactly ~session_id~, ~session_name~ and
  ~panes~. ~session_name~ is a nonempty, valid UTF-8 string; ~panes~ is a list,
  which may be empty.
- Each element of ~panes~ is an ADDRESS, carrying exactly ~pane_id~,
  ~window_index~, ~pane_index~ and ~registered_at_observation~. ~window_index~
  and ~pane_index~ are nonnegative integers, not strings.
- No other KEY appears. The raw census rows carry a path, a process id, a command
  string and a working directory; none of those fields is selected into this
  reply, and no key is added for them.

That is the whole of the guarantee, and it is a guarantee about SELECTED KEYS.
It is deliberately not a claim that nothing can be inferred from what is
published. ~session_name~ is operator-controlled text that this surface retains
verbatim: an operator who names a session after a path or a command has put that
text into the name, and publishing the name publishes it. Nothing here
sanitises, rewrites or inspects that text, and a reader must not take the list
above as a promise that omitted facts are unreachable.

The scope is narrower still in one respect worth naming rather than leaving to be
discovered. This slice governs the keys of the sessions REPLY. It does not newly
scrub telemetry the census already emits on its own path: the producer's tmux
boundary writes diagnostic text into OTel span status today (Orrisd 1018ad9b
~lib/ai_pair/tmux.ex~:760-790 with ~short_error~ at :834, called at :295), and
this contract neither changes that nor claims to have cleaned it. It is inherited
behaviour, named here so that the reply-shape guarantee above is not read as
covering it.

*** ~registered_at_observation~
:PROPERTIES:
:CUSTOM_ID: registered-at-observation
:END:
The field is named for what it is. ~registered_at_observation~ is true when the
pane was a member of ONE daemon pane-registry snapshot, keyed by ~pane_id~, taken
once after a successful census; it is replicated identically to every address of
that pane in the reply.

What it does NOT say, stated here beside the field rather than in a caveats
section a reader can skip: it is not liveness, not permission, not durable
intent, not readiness, not proof that the identity is valid, and it carries no
freshness interval. It is not an atomic observation either. The census and the
registry snapshot are two reads, in that order, and a pane may be registered,
unregistered or gone between them; the reply says what each read saw, not what
was simultaneously true. A caller that needs any of those properties must ask
for that property, and this surface does not offer one.

*** Linked windows: addresses, not pane objects
:PROPERTIES:
:CUSTOM_ID: linked-windows-addresses-not-pane-objects
:END:
A tmux window can be linked into more than one session, and into more than one
index of the same session. The same pane is then observable at several distinct
~(session_id, window_index, pane_index)~ addresses, and every one of them is a
real address rather than a duplicate record.

- Enumeration MUST NOT fail because a ~pane_id~ appears more than once. A
  projection that assumed globally unique pane ids would refuse an ordinary
  linked-window layout, so there is no global uniqueness rule here.
- What IS refused is a repeated address: the same ~(session_id, window_index,
  pane_index)~ twice in one reply, which is not a layout but a contradictory
  observation.
- Two contradictory ~session_name~ values for one ~session_id~ are refused for
  the same reason. Refusal is the answer, not reconciliation: the projection
  never picks a winner, and it never emits a second session object to carry the
  disagreement.
- A count of ~panes~ entries is a count of ADDRESSES. It is not a count of
  distinct panes, and a caller that wants distinct panes must reduce over
  ~pane_id~ itself.

*** Ordering
:PROPERTIES:
:CUSTOM_ID: sessions-ordering
:END:
The order is part of the contract, so that two observations of the same state are
the same ORDERED DATA: the same sessions in the same sequence, each carrying the
same addresses in the same sequence. That is an ordering rule over the values,
and nothing more. This document specifies no canonical JSON serialization: it
does not fix object key order, whitespace or line endings on the wire, and a
producer is not held to reproducing a pinned file byte for byte. The pinned
example files have exact bytes because they are pinned FILES; a real reply is
compared to one by decoding both and substituting the documented placeholders,
which is the convention the existing v2 fixture comparisons already use.

- ~sessions~ is sorted by ~session_id~ in BYTE order. This is a deliberate
  choice, not an accident of implementation: the stable id is treated here as an
  opaque presentation label, and sorting it as bytes keeps the rule true for any
  id the daemon has, without this document asserting anything about how the id is
  formed.
- ~panes~ within a session is sorted by NUMERIC ~window_index~, then NUMERIC
  ~pane_index~, then ~pane_id~ in byte order. These are actual positions, so they
  are compared as numbers.
- The two rules therefore disagree deliberately, and neither implies the other.
  Byte order and numeric order are NOT claimed to coincide anywhere: a session
  whose id ends in 10 sorts before one ending in 2, while window 2 sorts before
  window 10. The canonical examples contain both cases so that an implementation
  that applied one rule to both fields fails rather than passes.
- The ~pane_id~ tiebreaker exists to make the address order total. Because a
  repeated address is refused, two addresses within one session can never agree
  on both indices, so the tiebreaker is unreachable while that refusal holds. It
  is stated as a totality guarantee and is not an observable behaviour; no
  example can exercise it without first violating the refusal above.

*** The request, and why an unknown field is refused
:PROPERTIES:
:CUSTOM_ID: the-sessions-request
:END:
A ~sessions~ request carries ~cmd~ and ~protocol_version~, and may carry the
existing W3C trace carrier fields ~traceparent~ and ~tracestate~, which are
transport correlation and not application input.

Any other application field is refused with ~invalid_sessions_request~, and the
refusal precedes observation: the request is judged on what it carries, before
any census or registry read is attempted. The reason is the failure this refusal
prevents: a caller that sends a project or lifecycle filter this surface does not
have would otherwise be answered with the WHOLE census and no indication that its
filter was dropped, and would read that answer as filtered. Refusing is the only
behaviour that makes an unsupported filter visible to the caller who sent it.
This tightening applies to ~sessions~ only; legacy request acceptance on every
other command is unchanged.

*** Sessions identities
:PROPERTIES:
:CUSTOM_ID: sessions-identities
:END:
On THIS projection only, a ~session_id~ or ~pane_id~ is a prefix character -- ~$~
for a session, ~%~ for a pane -- followed by a nonempty run of decimal digits,
which is what tmux actually mints. An identity outside that grammar is a
malformed observation and is refused with ~invalid_sessions_census~.

This narrowing is deliberately local. The delivery identity grammar in
"Identity grammars and their refusals" above is wider, it governs what a receipt
can be keyed by, and it is NOT changed here; every existing v1 and v2 fixture
keeps its current identities and its current hash. Nonnumeric refusal is a
property of the sessions projection, tested on the sessions examples, and a
reader must not generalise it to ~send~ or ~reconcile~.

*** Sessions errors
:PROPERTIES:
:CUSTOM_ID: sessions-errors
:END:
Every error reply carries ~protocol_version~ 2 and ~ok~ false, and carries no
runner diagnostic: no stderr, no exit status, no command line, no path.

| Reply                                        | The observations it answers                                                                                      |
|----------------------------------------------+------------------------------------------------------------------------------------------------------------------|
| ~sessions.error.sessions_unavailable.json~   | The census failed, or the registry read failed. One reply for both: the caller is told the read did not happen, not which half of it did not happen. |
| ~sessions.error.invalid_sessions_census.json~ | The observation was malformed or self-contradictory: a bad row, an identity outside the sessions grammar, a repeated address, or two names for one ~session_id~. |
| ~sessions.error.invalid_sessions_request.json~ | The request carried an application field this surface does not accept.                                           |
| ~oversize.json~                              | The GENERIC v2 oversize refusal, not a sessions-specific error.                                                  |

The four files are four distinct replies because they are four distinct wire
answers. Causes that share a reply share a file: a failed census and a failed
registry read are indistinguishable to the caller on purpose, and giving them two
filenames would have implied a distinction the contract refuses to make.

There is no ~sessions_oversize~. A reply too large to send is refused with the
generic v2 oversize error, and the refusal is a producer decision made BEFORE the
bytes are handed to the socket: the candidate reply is encoded, its payload byte
length is measured, and a length above 1048576 bytes is answered with the small
static oversize reply instead. Packet-size receiver settings do not provide this.
A receiver limit fails the frame, or closes the connection, or truncates -- what
it never does is produce a typed refusal the caller can read, which is the whole
point of the outcome. The refusal reply is static and small, so it can never
itself exceed the bound it enforces.

*** What a timeout means: an inherited limitation, not a bound
:PROPERTIES:
:CUSTOM_ID: what-a-timeout-means
:END:
This section records a limitation this surface INHERITS and does not close. It is
here because a reader would otherwise infer a guarantee from the presence of
deadlines.

A timeout means the CALLER became unavailable. It does not mean the work was
cancelled. The server accepts at most 32 concurrent connection handlers, the
caller receive deadline is 5 seconds and the tmux call deadline is 5 seconds.
None of those bound the census work that accumulates after repeated caller
timeouts while the single tmux process is blocked in a synchronous subprocess
call: the deadline releases the caller, the subprocess keeps running, and the
next queued call waits behind it.

No retry is introduced by this command, because a retry against an uncancelled
queue adds work to the thing that is already behind. This slice adds no
subprocess machinery and makes no claim to have closed the limitation. Bounding
tmux execution globally is a separate scope with its own source and control
review; a sentence here promising it would be a guarantee nothing implements.

*** One read, and what it never does
:PROPERTIES:
:CUSTOM_ID: one-read-and-what-it-never-does
:END:
An ADMITTED ~sessions~ request performs exactly one strict census read and, only
if that census succeeded, one read-only registry snapshot. It performs no attach,
no detach, no marker update, no repair, no send, no reconciliation, no receipt
admission and no retry.

Admission comes first, and the distinction matters because the two rules would
otherwise contradict each other. A request carrying an application field this
surface does not accept is refused with ~invalid_sessions_request~ BEFORE any
observation: no census runs, no registry is read, and the count for that request
is zero reads rather than one. "Exactly one census" is therefore a statement
about requests that were admitted, and a refused request is not a cheaper path
through the same work but a refusal that happens before the work exists. A control that proves this asserts the absence of those
calls with an injected double, and the corresponding positive witness must make
the negative control fail.

A census that returned nothing is a success carrying an empty ~sessions~ list. A
census that FAILED is never reported as an empty success and never as partial
output: the whole reply is refused. An absent session and an unreadable machine
are different facts, and this surface keeps them different.

The hash rule is the v1 rule, unchanged: byte-sorted ~*.json~ filenames, each
followed by a NUL byte, its exact bytes and another NUL byte, hashed as SHA-256,
stored as 64 lowercase hex characters and a final newline. The directory and
~CONTRACT_HASH~ itself are not inputs. The v1 contract keeps its own fifteen
fixtures and its own hash, and nothing in this section touches either.

The eight successful examples, and what each one is for:

| Example                                       | What it holds the projection to                                                                     |
|-----------------------------------------------+-------------------------------------------------------------------------------------------------------|
| ~sessions.ok.empty.json~                      | A census that saw nothing is a success with an empty list, which is not the same answer as a failure.   |
| ~sessions.ok.multiple_sessions.json~          | Several sessions, several addresses in one window; the ordinary shape.                                  |
| ~sessions.ok.duplicate_names.json~            | Two sessions with the same ~session_name~ and different ~session_id~ values: the name is reusable, the id is the identity. |
| ~sessions.ok.mixed_registration.json~         | Two addresses in one session disagreeing on ~registered_at_observation~, so an implementation cannot answer a constant. |
| ~sessions.ok.linked_window.json~              | One ~pane_id~ at addresses in two sessions: enumeration succeeds, and the two entries are not duplicates. |
| ~sessions.ok.multi_address_consistency.json~  | One pane at three addresses across two sessions and two windows, with its registration replicated identically -- and false, so a default cannot pass for a reading. |
| ~sessions.ok.ordering.json~                   | Byte order and numeric order disagreeing in the same file: ids ending 10, 2, 9 in that order, windows in 0, 2, 10 order and panes in 0, 1, 2, 10 order. |
| ~sessions.ok.escaped_names.json~              | A ~session_name~ carrying a quote, a backslash, the census field separator, a tab, a newline and non-ASCII text, none of which may break the projection. |

What no example can hold is the ~pane_id~ tiebreaker, which is unreachable while
repeated addresses are refused, and the byte length boundary, which is a rule
about an encoded candidate rather than a shape: the control constructs values at
1048576 and 1048577 bytes instead of storing them.

That boundary control is ILLUSTRATIVE ARITHMETIC and nothing more. It shows what
the documented predicate decides on either side of the bound, using a locally
built value and a local byte-size test. It is not evidence about the producer: it
does not measure the producer's threshold, its encoder, where in its reply path
the check sits, or whether it ever hands an oversized payload to the socket. The
controls that would establish those facts are owed by the implementation and
remain owed; no result in this repository discharges them.

They are separate for two reasons, and only the second is about tidiness. The
first is that the paired v2 set is equal on both sides of a pairing this document
records; adding an example the producer has never emitted would make that
equality false while leaving the block asserting it.

The second is mechanical and belongs to the PRODUCER, which is where the
consequence lands. The producer's delivery-fixture harness -- Orrisd
~test/ai_pair/ipc/contract_v2_fixture_test.exs~:94-116 at 1018ad9b -- enumerates
every JSON file in that directory and dispatches each one through
~Delivery.dispatch~ with a closed prepare mapping. A sessions example dropped in
beside the delivery fixtures would therefore be driven down the delivery route on
vendoring, which is the wrong producer path and proves nothing about this
surface. The consumer tests in this repository do not have that problem, because
they select ~send.*~ and ~reconcile.*~ by glob rather than enumerating the
directory; the reason for the separate directory is cross-repository, and stating
it as a fact about local consumer tests would be wrong.

~sessions_example_status~ is a claim about the world, not a label. It read
~unadopted~ while no producer emitted these bytes, and it was written to move when
a producer did, together with the ping example and the pairing block, in a change
that measures the producer rather than predicting it. That is the change this
revision makes, and the measurement is the reason.

At the producer snapshot named as ~sessions_example_adopted_at~ and as
~paired_revision~, orrisd ~7e5f5321~, the producer's own production-path suite
~test/ai_pair/ipc/sessions_contract_fixture_test.exs~ drives its production
dispatch, projection and encoding with injected census and registry observations,
and asserts decoded semantic equivalence with each of the eight successful
examples and each of the four refusals in this directory after placeholder
normalization, not raw emitted bytes;
its ordinary v2 ping advertises ~sessions_read~. The twelve files here are
byte-identical with the twelve that snapshot carries. ~adopted~ therefore records
something measured at a named commit.

What it does NOT say, and what no reader may take from it: that the producer's
main branch carries this, that any released or installed daemon answers
~sessions~, or that the pairing tracks the producer's current head. It is a
snapshot claim. A later producer revision re-vendors this file and changes the
producer document again; that creates the next re-pairing to measure and leaves
this one exactly as true about ~7e5f5321~ as it is today. Whether a given daemon
answers ~sessions~ stays a runtime discovery through the capability preflight,
never an inference from this block.

The separation of the two directories is unchanged by adoption and is not a
consequence of it: the sixteen delivery fixtures and these twelve examples remain
two distinct inventories for the cross-repository reason given above, and neither
count moved.

*** The CLI binding
:PROPERTIES:
:CUSTOM_ID: the-sessions-cli-binding
:END:
- The CLI defaults ~sessions~ to protocol version 2. This command has no v1
  form, so there is nothing for a default to lose.
- An explicitly requested v1 ~sessions~ is REFUSED. It does not fall back to v2,
  and it does not fall back to any local enumeration: a caller that asked for a
  version is answered about that version.
- Capability preflight comes first. The CLI pings, and without ~sessions_read~
  in the answer it refuses without ever sending a ~sessions~ request. An old
  daemon is therefore refused by the preflight rather than by a request it cannot
  parse.
- Success and error exit conventions are the existing ones; this command
  introduces none of its own.

** Placeholders
:PROPERTIES:
:CUSTOM_ID: placeholders
:END:
~<msg_id>~, ~<pane_id>~, ~<payload_hash>~ and ~<version>~ are dynamic and are
substituted by the consumer tests; everything else is exact bytes.

The sessions examples add ~<pane_id_1>~ through ~<pane_id_8>~, one placeholder
per distinct pane within a file, substituted the same way. They are placeholders
for a measured reason rather than a stylistic one: the redaction gate
(~bin/redaction-check~) refuses a literal tmux pane id anywhere in the tree, so a
pane id cannot be written into a tracked file, and the existing v2 fixtures use
~<pane_id>~ for exactly that reason. Session ids are under no such gate and are
written as exact bytes, which is what lets the ordering examples show byte order
being applied to ids and numeric order to indices in the same file.
