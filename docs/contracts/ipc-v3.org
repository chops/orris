** Implementation status
:PROPERTIES:
:CUSTOM_ID: implementation-status
:END:
The identity core below is implemented on both sides and paired (see
"Pairing"): the producer (the ai-pair daemon, Orrisd, at the paired revision)
serves it, and the consumer in this repository reads version 3 ~status~ for its
claim checks (NS-15.G.002 B1c). ~cancel~ and ~subscribe~ remain specified and NOT
implemented on either side. ~release~ (NS-15.G.003 S3, below) is implemented by the
producer at the paired revision (NS-15.G.003 S3a), which advertises it in its durable
version 3 ~ping~ (~ping.ok.identity_core_release.json~, the paired ping); this consumer
does not send it. Every release-command request and reply file (~v3_request.release.json~,
~v2_request.release.json~, ~release.released.json~, ~release.error.*.json~ and
~v2_reply.release.unsupported_command.json~) is an example and unclaimed: a
release-command reply becomes claimable only once a producer test obtains it from the
real dispatch path and compares it with the file, and a release-command request only
once a producer test sends it
unchanged through the real dispatch path and receives its paired reply; in both cases
this text changes first. No client may send a version 3 request until the
daemon advertises the capability tokens below in a version 3 ~ping~. Version 2
(~ipc-v2.org~) is unchanged and stays the wire for every existing client; a daemon
serves both versions side by side. An installed daemon older than the paired
revision does not speak version 3; installing the paired pair is a separate,
held step, and until then this consumer refuses identity-gated claims against
such a daemon rather than downgrading them.

The fixture bytes in ~test/fixtures/contracts/ipc/v3/~ are the version 3 shapes
this repository pins, with their ~CONTRACT_HASH~ computed under the v1 hash rule
(see ~ipc-v1.org~), checked by ~test/contracts/ipc_v3_contract_hash_test.exs~.
Each belongs to one of the classes below. The /core reply/ files are the frames
the paired producer emits from its real dispatch path (placeholders aside, and
compared after decoding); the bytes here did not change at pairing. The two
/client request/ files are exercised unchanged by the paired producer. The
/example/ files are written from this text and stay shape only until the feature
that would produce them is implemented and this text changes first.

*** Identity core
The first producer implements a bounded subset, the /identity core/: ~ping~,
~status~, ~send~ and ~reconcile~ at version 3 with ~pane_identity~, the
~pane_identity_unavailable~ refusal, and the version 2 refusal of version 3
commands. ~cancel~ and ~subscribe~ stay specified and are not part of it; a daemon
that implements only the identity core advertises ~pane_identity~ and neither
~cancel~ nor ~subscribe~, so no client sends them. ~ping.ok.identity_core.json~ is
the ping of such a daemon without ~release~ (an example since S3a); the paired
producer also implements ~release~ and answers ~ping.ok.identity_core_release.json~,
a core reply. Since NS-32.M.001 RB-1 the paired producer also reports its build
identity: when it read a valid record it answers
~ping.ok.identity_core_release_build.json~ instead, also a core reply; without one it
still answers ~ping.ok.identity_core_release.json~, so both are core replies.

Every fixture belongs to exactly one class:
- /core reply/: a reply the identity-core producer emits byte for byte
  (placeholders aside). These are the only files a pairing replaces with produced
  frames.
- /client request/: a request frame a client sends. The daemon never produces it.
  It counts as an exercised request only once a producer test sends it unchanged
  to the real dispatch path and receives its paired reply.
- /example/: shape only, including every ~cancel~, ~subscribe~, event, loss and
  sequence file, the full-token ~ping.ok.json~, the client-side
  ~ping.missing_tokens.json~, and the negative ~send.sent.no_pane_identity.json~,
  which a correct daemon never emits. An example stays an example until the
  feature that produces it is implemented and this text changes first.
The class of each file is listed in the example set below. No file is a produced
frame until a pairing records it.

What version 3 adds, and why each piece exists:
- pane identity in every pane-bound reply, so a pre-dispatch claim check can tell
  a registration apart from a later one on the same tmux pane;
- a per-pane ~status~ read for observation without the version 1 ~pane_status~;
- ~cancel~, which withdraws a queued send and never un-pastes one;
- ~subscribe~, a pushed stream of pane, receipt and registration changes, so a
  client polls only when the stream is lost;
- ~release~, which lifts a restored pane's quarantine after the daemon proves its
  pane identity, and pastes only the restored sends bound to that identity.

** Framing and version
:PROPERTIES:
:CUSTOM_ID: framing-and-version
:END:
- A request that carries ~"protocol_version": 3~ is a version 3 request. Every
  version 3 reply and frame carries ~"protocol_version": 3~ and ~ok~. Every reply to
  a message-bound command echoes ~msg_id~ and ~pane_id~, as in version 2. A reply
  without the version, or a version 2 reply to a version 3 request, is not a
  version 3 answer and a client MUST refuse it.
- ~ping~ at version 3 answers ~capabilities~. The tokens this version defines are
  ~pane_identity~, ~cancel~, ~subscribe~ and ~release~; ~delivery_reconcile~ keeps its version
  2 meaning. A client MUST NOT send a command whose token is absent and fails closed
  instead (~ping.missing_tokens.json~). Unknown well-formed extra tokens are
  admissible.
- ~build_identity~ is an informational token: it names no command. A daemon
  advertises it in its version 3 ~ping~ only when it read a valid identity record of
  its own build, and then the ~ping~ also carries a ~build_identity~ object; without
  a valid record both the token and the object are omitted (there is no typed
  "unavailable" value). The object has exactly these keys:
  - ~name~ and ~version~: strings;
  - ~source_revision~: 40 lowercase hex, or ~null~ when the build was not made from a
    clean revision;
  - ~clean~: boolean;
  - ~source_nar_hash~: a string beginning ~sha256-~;
  - ~build_id~: 64 lowercase hex, the sha256 of the build's canonical INPUT identity
    (name, version, source NAR hash, lock-file hash, pinned dependency hash, target
    system, release name, IPC protocols, in that order), never a digest of the built
    artifact; a client compares it byte for byte and does not interpret it;
  - ~ipc_protocols~: a list of integers;
  - ~rollback_eligible~: true exactly when ~clean~ is true and ~source_revision~ is 40
    lowercase hex.
  A client MUST NOT treat a missing ~build_identity~ as an identity. The example
  values in ~ping.ok.identity_core_release_build.json~ (eligible) and
  ~ping.ok.identity_core_release_build_dirty.json~ (not eligible) are synthetic; a real
  daemon reports its own build. The eligible one is a core reply: the paired producer's
  real dispatch path, given that record, emits exactly it. The dirty one stays an
  example. Version 1 and 2 ~ping~ are unchanged.
- A version 2 request naming a command that exists only in version 3 (~subscribe~,
  ~cancel~, ~status~ or ~release~) is refused by the daemon with ~unsupported_command~ in a
  version 2 reply that echoes ~cmd~ and any ~msg_id~ / ~pane_id~ the request carried.
  The refusal has no side effect: no subscription opens, no receipt changes, nothing
  is pasted, and it never hangs. The pairs ~v2_request.subscribe.json~ /
  ~v2_reply.subscribe.unsupported_command.json~ and ~v2_request.cancel.json~ /
  ~v2_reply.cancel.unsupported_command.json~ show it, and so do the example pair
  ~v2_request.release.json~ / ~v2_reply.release.unsupported_command.json~. These six files, and the
  ~request~ / ~reply~ inside the ~scenario.*~ files, are the only version 2 bytes in
  this set.
- ~send~ and ~reconcile~ keep their version 2 requests, grammars and refusals.
  Their version 3 replies add ~pane_identity~ (~send.sent.json~,
  ~send.queued.json~, ~reconcile.queued.json~, ~reconcile.delivered.json~);
  ~reconcile~ adds the outcome ~cancelled~ (below).
- ~pane_identity_unavailable~: a daemon that cannot produce a complete
  ~pane_identity~ for a pane (for example one that mints no registrations, or one
  without a pane-intent generation) refuses every version 3 pane-bound command --
  ~status~, ~send~ and ~reconcile~ -- with ~ok: false~ and error
  ~pane_identity_unavailable~ in a version 3 reply that echoes ~pane_id~, and
  ~msg_id~ for ~send~ and ~reconcile~
  (~status.error.pane_identity_unavailable.json~,
  ~send.error.pane_identity_unavailable.json~,
  ~reconcile.error.pane_identity_unavailable.json~). The refusal comes before any
  effect: no receipt is admitted or changed and nothing is pasted. Such a daemon does
  not advertise ~pane_identity~ in its version 3 ~ping~. It never answers a version
  3 pane-bound command with success without ~pane_identity~. A client treats the
  refusal as the daemon being unavailable for an identity-gated claim and does not
  dispatch. Version 1 and version 2 are unchanged.

** Pane identity
:PROPERTIES:
:CUSTOM_ID: pane-identity
:END:
- ~pane_identity~ is ~{pane_id, registration_id, generation}~. ~registration_id~ is
  minted by the daemon when a pane is attached and is never reused; a pane that is
  detached and attached again, even on the same tmux pane id, is a NEW registration
  with a new ~registration_id~. ~generation~ is the pane-intent record generation the
  daemon's boot reconciliation already compares. On the wire it is a JSON STRING of
  one or more decimal digits (~[0-9]+~), exactly the pane-intent record's
  ~session_gen~ and the session marker's generation in the daemon, which mint it from
  16 random bytes rendered in decimal (1 to 39 digits) and compare it as text. It is
  never converted to a number: it can exceed any fixed-width integer, and a client
  compares it byte for byte.
- ~registration_id~ is ~reg_~ followed by exactly 32 lowercase hex characters. It
  appears only in replies and frames; no version 3 request carries one. A client
  that reads a ~registration_id~ outside this grammar, or a ~generation~ that is not
  a string of decimal digits (a JSON number included), refuses the reply as a reply-identity error, exactly as it
  refuses a mismatched ~msg_id~ or ~pane_id~ echo in version 2, and never uses it for
  a claim comparison.
- Which replies carry ~pane_identity~: every version 3 reply or frame that reports a
  receipt or the state of a registered pane -- ~send~ results and duplicates,
  ~reconcile~ outcomes that carry a receipt view (~delivered~, ~queued~,
  ~ambiguous~, ~cancelled~), ~cancel~ outcomes that carry a receipt view
  (~cancelled~, ~too_late~, ~ambiguous~), successful ~status~ and ~release~, every snapshot entry
  and every pane or registration event. Replies that name no registration omit it:
  ~reconcile~ and ~cancel~ ~absent~ and ~conflict~ (no stored record, or the caller's
  identities only), every refusal (~ok: false~, for example ~pane_not_found~ and
  ~pane_identity_unavailable~), and
  ~ping~ and ~subscription_lost~. A client MUST NOT require ~pane_identity~ on those
  and MUST NOT treat its absence there as proof of anything about the pane.
- A client holding a claim for a pane MUST compare the reply's ~registration_id~ and
  ~generation~ with the identity recorded in its claim before dispatch; a reply that
  should carry ~pane_identity~ but does not (~send.sent.no_pane_identity.json~), or a
  mismatch, refuses dispatch and opens a diagnosis that names the pane, the claim and
  the observed daemon state.
- The process id of the pane is NOT identity: tmux ~respawn-pane~ keeps the pane id
  and changes the pid. It appears only in ~status~ as ~pane_pid~.

** Status
:PROPERTIES:
:CUSTOM_ID: status
:END:
- ~status~ ~{pane_id}~ answers ~state~, ~quarantined~, ~queue_depth~, ~pane_pid~ and
  ~pane_identity~ (~status.ok.json~, ~status.quarantined.json~), or a typed refusal
  such as ~pane_not_found~ (~status.error.pane_not_found.json~) or
  ~pane_identity_unavailable~ (above).
- It is a per-pane read. The registry-wide read and its JSON shape are not defined
  here.

** Release
:PROPERTIES:
:CUSTOM_ID: release
:END:
Specified (NS-15.G.003 S3; Charles decisions 49 and 50) and implemented by the
producer at the paired revision (S3a); this consumer does not send it. A daemon
advertises ~release~ in its version 3 ~ping~ only when it implements it, in durable
mode (~ping.ok.identity_core_release.json~); a client MUST NOT send it otherwise.

- Request ~release~ ~{pane_id}~ (~v3_request.release.json~). It applies to a pane the
  daemon restarted quarantined after a daemon restart.
- Under the pane's lock the daemon first proves the pane's exact ~pane_identity~
  (~registration_id~ and ~generation~), exactly as for ~status~. It then replaces the
  quarantined pane with an unquarantined one bound to that identity. The proof stays
  valid, and the daemon refuses to revoke it, from before each paste command until
  tmux acknowledges that command.
- Restored sends recorded with that exact ~{registration_id, generation}~ are pasted
  in their original order. Restored sends recorded with no pair, or another pair, are
  /held/: never pasted, kept and listed, and still counted against queue capacity.
  No send is finalized or deleted by ~release~.
- Success (~release.released.json~) answers ~released: true~, ~pane_identity~ and
  ~counts~ ~{matched, held}~ at the moment of release. It reports the decision, not
  delivery; each send's outcome is read with ~reconcile~.
- Delivery guarantee: the guarantee ends at each paste command's terminal outcome,
  the exit of the tmux client the daemon started for it. The proof stays valid
  until that outcome. Three cases are distinct:
  - exit 0: tmux acknowledged the command; the send is ~delivered~;
  - any other exit: the command completed without that acknowledgement; the send is
    ~ambiguous~ and the pane is not held;
  - no terminal outcome (tmux, the daemon or its store died first): the send is
    ~ambiguous~ and the pane is held. No further proof, release or paste happens
    for it until a later decision.
  An acknowledgement does not confirm that the bytes reached the pane, and this
  contract claims nothing beyond it.
- Refusals, each a version 3 reply that echoes ~pane_id~ and carries no
  ~pane_identity~, and each before this release operation pastes anything:
  - ~pane_identity_unavailable~: the identity could not be proven
    (~release.error.pane_identity_unavailable.json~);
  - ~effect_unresolved~: the pane is held after a paste command with no terminal
    outcome (~release.error.effect_unresolved.json~);
  - ~release_fence_unavailable~: the pane's lock is held or a paste command is still
    in flight (~release.error.release_fence_unavailable.json~);
  - ~release_stop_failed~: the quarantined pane could not be stopped; it stays
    quarantined (~release.error.release_stop_failed.json~);
  - ~release_failed_requarantined~: the unquarantined pane could not be started, and
    the pane was started quarantined again
    (~release.error.release_failed_requarantined.json~);
  - ~release_unstarted~: neither could be started; the pane has no running process
    and its sends stay queued and listed (~release.error.release_unstarted.json~).
- Version 2 refuses ~release~ with ~unsupported_command~ (~v2_request.release.json~ /
  ~v2_reply.release.unsupported_command.json~).
- A released state does not survive a daemon restart: the pane comes back
  quarantined and must be released again.

** Cancel
:PROPERTIES:
:CUSTOM_ID: cancel
:END:
- ~cancel~ carries ~msg_id~ and ~pane_id~ and answers exactly one ~outcome~:
  | outcome     | meaning                                                                                         |
  |-------------+-------------------------------------------------------------------------------------------------|
  | ~cancelled~ | the send was queued and is withdrawn; its receipt is now ~cancelled~                            |
  | ~too_late~  | the send was already delivered; nothing changes                                                 |
  | ~ambiguous~ | the paste is in flight or pending; the daemon does not wait for it and nothing is withdrawn     |
  | ~absent~    | no receipt exists for these identities                                                          |
  | ~conflict~  | the ~msg_id~ exists with a different pane; echoes the identities presented, never the stored ones |
- ~cancel~ never pastes and never un-pastes.
- ~cancelled~ is a NEW TERMINAL receipt status, distinct from ~not_delivered~. It is
  never stored as ~not_delivered~, because version 2 admission opens a new attempt
  for a ~not_delivered~ receipt and a cancelled send MUST NOT be re-admitted.
- At version 3, ~reconcile~ of a cancelled send answers the sixth outcome
  ~cancelled~ with the receipt view (~reconcile.cancelled.json~), and a ~send~ that
  repeats its ~msg_id~ is refused as a duplicate with ~status~ ~cancelled~
  (~send.duplicate.cancelled.json~).
- At version 2 a cancelled receipt is read as ~ambiguous~: a version 2 ~reconcile~
  answers the existing ~reconcile.ambiguous~ shape and a version 2 duplicate answers
  ~send.duplicate.ambiguous~. Version 2 already requires a client to refuse
  ~ambiguous~ and never resend it, so a version 2 client can neither re-admit nor
  report delivery for a cancelled send. No version 2 shape changes. The two
  projections are shown as scenarios: ~scenario.cancelled.v2_reconcile.json~ and
  ~scenario.cancelled.v2_send.json~ each name the state they start from
  (~cancel.cancelled.json~), the version 2 request, and the reply, which is
  structurally equal (same keys and values once decoded) to the existing version 2
  fixture it names in ~projection_of~; that fixture's own bytes stay pinned by the
  version 2 hash, so the projection uses the unchanged version 2 shape.

** Subscribe
:PROPERTIES:
:CUSTOM_ID: subscribe
:END:
*** Frames
- ~subscribe~ ~{panes: [pane_id, ...]}~ or ~{panes: "all"}~ opens a dedicated
  connection. The first frame is a ~snapshot~ (~seq~ 0); later frames are ~event~
  frames with a per-subscription ~seq~ that increases by exactly 1, or one
  ~subscription_lost~ frame before close.
- Event ~kind~ values: ~pane_state~, ~receipt~, ~pane_gone~ and ~registration~
  (~change~ ~attach~ or ~detach~).
- Each pane has a ~version~ that increases by exactly 1 on every observable change.
  Every snapshot entry and every pane event carries it. Registering the subscriber
  and reading a pane's snapshot entry happen in one serialized step of that pane's
  owner, so the first event for a pane carries the snapshot entry's version plus 1.

*** Subscribe to all panes: the registry handoff
- Membership has one serializing owner, the registry, with a ~registry_epoch~ that
  increases by exactly 1 on every attach and every detach. Everything below is keyed
  by ~registration_id~, never by ~pane_id~ alone.
- Each subscriber has one outbound queue. Enqueue appends to a bounded buffer and
  returns; it never waits on the client socket.
- Capture: in one registry step the daemon adds the subscriber and records the
  member set M (registration ids) and the epoch E. From then on every attach and
  detach is enqueued to this subscriber as a ~registration~ event with its epoch;
  the first carries E + 1.
- Tombstones: until this subscriber's snapshot is emitted, a member of M that
  detaches leaves a tombstone with its final entry. A pane owner that terminates
  abnormally leaves a tombstone with ~final_state~ ~unknown~ and no version, and the
  registry treats that termination as a detach. Tombstones are released when every
  pending subscriber that pinned them has emitted its snapshot or closed; a pending
  subscriber whose snapshot is not emitted within a fixed deadline is closed (reason
  ~snapshot_timeout~, or a bare close).
- Snapshot read: each entry is read from the owner of THAT registration id. If the
  owner has stopped, or the pane id now belongs to another registration, the
  tombstone is used and the entry is marked ~detached~. A new registration on the
  same pane id never enters this snapshot; it arrives only as its own attach event.
- The snapshot frame carries ~epoch~ (E) and ~max_epoch_at_snapshot~, the registry
  epoch when the last entry was read. With an empty M, ~max_epoch_at_snapshot~ is E
  (~subscribe.all.empty.json~).
- Attach is one registry step in this order: mint the registration id and advance
  the epoch; enqueue the attach event, carrying the initial entry at version 0, to
  every all-panes subscriber including pending ones; only then start the pane owner.
  The owner does not exist before every enqueue has returned, so no pane event can
  precede its registration on any subscriber's queue.
- Detach is one registry step: stop admitting sends for that registration, write any
  pinned tombstones, stop the owner, advance the epoch, enqueue the detach event.
- Events produced between capture and the snapshot frame wait in the subscriber's
  queue, count against its bound, and are sent after the snapshot frame in enqueue
  order.
- A snapshot captures STATE at the version each entry was read, not the transitions
  between capture and that read; the version number is the only trace of them.

*** Client view and protocol errors
- The view is keyed by ~registration_id~. An entry marked ~detached~ is in view as
  detached-pending and pairs with exactly one later detach event, which removes it;
  it causes neither a second detach nor a resubscribe.
- Each of these is a protocol error that makes the client discard its view and
  resubscribe: a ~seq~ gap or repeat; a pane ~version~ gap, or an event at or below
  the version in view; an epoch gap or repeat; an attach for a registration already
  in view; a detach for a registration not in view; a pane event for a registration
  not in view or detached-pending; a detached-pending entry still unmatched after
  every registration event up to ~max_epoch_at_snapshot~ has been applied.

*** Loss, overflow and restart
- Overflow: when a subscriber's buffer is full the daemon stops enqueueing for it,
  writes ~subscription_lost~ ~{reason: overflow}~ only if that write would not block,
  and closes either way. Delivery and other subscribers are never slowed by a slow
  subscriber.
- Restart: subscriptions are not durable. A daemon restart closes them with no final
  frame.
- A final frame is NOT guaranteed. A bare close (~seq.close_no_frame.*.json~) is a
  complete loss signal, classified the same as the matching ~subscription_lost~
  frame; it does not require one.
- What ~seq~, ~version~ and ~epoch~ prove: only that this stream has no gap. They
  never prove a delivery outcome. Delivery truth comes only from ~reconcile~.

*** After loss
- The client discards its view and treats every pane state it held as UNKNOWN. It
  reconciles every send that is not terminal in its journal before any other action;
  ~ambiguous~ raises attention and is never resent; a resend happens only after
  ~reconcile~ answers ~absent~.
- It resubscribes with bounded backoff and meanwhile observes with version 3
  ~status~. A status reply clears UNKNOWN for that pane only when it arrived after
  the loss, succeeded, carries a ~pane_identity~ equal to the identity in that pane's
  claim, and reports the pane live and not quarantined. A stale, missing, failed or
  contradictory reply never clears it; it refuses dispatch to that pane and opens the
  claim-refusal diagnosis. No dispatch goes to an UNKNOWN pane.
- Degraded polling is bounded. Dispatch to cleared panes continues only with a fresh
  identity-matching ~status~ before each dispatch. A snapshot before a fixed
  deadline ends degraded mode. At the deadline without one, the run reaches attention
  ~daemon_subscription_degraded~ and dispatches nothing more. If resubscription and
  ~status~ both fail past a fixed deadline, the run reaches attention
  ~daemon_observation_lost~. A later snapshot never resolves either attention or
  resumes dispatch; only an authorized ~resolve_attention~ does, after a snapshot
  received since the attention opened, identity checks of the panes to be
  dispatched, and reconciliation of the non-terminal sends.

*** Bounds
The per-subscriber buffer size, the snapshot deadline, the resubscription backoff,
the status poll interval and the two attention deadlines are fixed and finite. Their
values are chosen with the first producer and consumer tests and recorded here then;
until they are, no implementation may claim conformance.

** Placeholders
:PROPERTIES:
:CUSTOM_ID: placeholders
:END:
~<msg_id>~, ~<pane_id>~, ~<payload_hash>~, ~<version>~, ~<text>~,
~<registration_id>~ and ~<generation>~ are dynamic and substituted by tests (a
substituted ~registration_id~ or ~generation~ follows its grammar above); ~<pane_id_1>~, ~<pane_id_2>~ and
~<registration_id_1>~ to ~<registration_id_3>~ name distinct panes and registrations
within one file. Pane ids are placeholders because ~bin/redaction-check~ refuses a
literal tmux pane id in the tree. Everything else is exact bytes.
